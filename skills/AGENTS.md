# skills

## Purpose

- Canonical authored and adapted skill trees.

## Ownership

- Each direct child directory is a category grouping (`engineering/`, `tools/`, `productivity/`, `misc/`, `in-progress/`); each skill leaf is one complete directory nested one level under its category.
- Root `skill-harnesses.nix` owns sparse logical harness routing.
- Root `skill-selection.nix` owns global selection exclusions.

## Local Contracts

- Preserve each whole tree, including scripts, references, assets, licenses, fixtures, and test material.
- Skills absent from `skill-harnesses.nix` are logical common.
- Routed skills belong only to their named logical harness, not common.
- Authored/adapted leaves have no `skills-lock.json` entry.
- Excluded authored leaves remain canonical here and may have one matching relative project projection at `.agents/skills/<name>` → `../../skills/<category>/<name>`.

- `productivity/orchestrate-using-t3code/` owns user-invoked T3 Code orchestration of tasks agreed in conversation before invocation. Invocation counts as the user's request for one top-level worker thread per task. Workers are `t3_thread_launch` threads in their own worktrees (`workspaceStrategy` worktree; `startFromOrigin: false` for stacked bases), Pi by default, inheriting the orchestrator's runtime mode; approvals go to the user, questions are answered with `t3_pending_request`. The orchestrator uses T3 MCP tools for every action and the `t3` CLI only in scripts. Startup reads its own thread ID from `t3_thread_list`, prefixes its title with `[o]` without doubling, and pins it. PRs are linked to worker threads and watched on the orchestrator thread with `watch_pull_request`. `scripts/` own startup (`orchestrate-init.sh`: T3 and `t3` CLI check, per-thread log path outside every repo), the thread watcher (`watch-thread.sh`: `t3 thread show --json` until the latest run settles, 30-second re-check), the TSV task log (`log.sh`), pinned pushes (`push-pinned.sh`), and resource reaping (`reap-worker.sh`); `references/` own preflight (base via `land-change`, naming, launch, returned-path and HEAD confirmation), supervision (background watchers or foreground `t3_thread_wait`, PR link and watch, steering by `t3_thread_send`), worker context (Keep, Compact, Handoff and New through replacement threads bound to the existing worktree), reaping (thread stop, `reap-worker.sh`, `git worktree remove`, local branch delete after merge), and per-kind `agent-quirks.md`; `evals/evals.json` owns focused scenarios. It has no `tests/` folder. `docs/specs/orchestrate-using-t3code.md` records its design.
- `productivity/orchestrate-using-herdr-app/` owns user-invoked orchestration on herdr-app with herdr-core (`hc`), including invocation, sticky-mode, authority, brief, `--track`, `--watch`, `--auto`, worker-context, and report contracts. Workers are hidden background `hc` terminals, children of the orchestrator's `$HC_TERMINAL_ID` started with `--outlive-parent`; `herdr-app` changes the user's window only on request. Reporting is pull-only: workers start with `hc run --no-notify` and report by ending their turn, never `hc send` to the orchestrator (follow-up messages restate this because `hc` adds `reach=` hints); the orchestrator learns state only from `watch-agent.sh` and `hc read` (without supervision, only when the user asks), so nothing types into the user's input. A peer orchestrator the user asks for runs top-level in a visible `herdr-app do tab.new` tab with no parent, owns its own workers, and is watched and read the same way. Under `--watch`/`--auto`, a worker pushes and reports "ready to create PR"; the orchestrator sizes the diff (docs-only skip, `low`, `high`), runs one pre-PR review by a reviewer `hc` worker of the other kind in the same worktree (Claude: built-in `/code-review <level> <branch>`; Pi: `$skill:axis-review`, posting and changing nothing), routes findings back, then releases the PR; later rounds review only commits since the last reviewed head and block only on correctness bugs, real runtime or security risks, and unfixed findings, with cleanup going to the PR body as follow-ups; post-PR repairs get no pre-PR review. Every follow-up brief goes through `send-followup.sh`, which sends to a live worker and revives a finished one with a `resume` label (hibernated or `stopped_by_restart`) via `start-worker.sh --resume`. Worktrees come from plain `git worktree add` at `~/.herdr/worktrees/<repo>/<agent>` from the parent source. `scripts/` own startup (`orchestrate-init.sh`: `hc` and `$HC_TERMINAL_ID` check, log path keyed by terminal ID outside every repo), worker startup (`start-worker.sh`: `--no-notify`, name pattern `[a-z][a-z0-9_-]{0,31}`, `env AGENT_BROWSER_NAMESPACE=<name>` because `hc` terminals do not inherit the caller's environment, labels `hibernate=ok` and `space=<id>` from the orchestrator's `space` or `herdr.space` label, the brief as the agent's argv first message, `codex --no-daemon`, confirmation by turn count because `hc wait` can report `idle` before the brief submits, exit 2 when unconfirmed), follow-up delivery (`send-followup.sh`: `hc send` to a live worker, exit 2 when blocked or unresumable, otherwise `hc rm` and `start-worker.sh --resume` with the kind and session parsed from the `resume` label), the settled-agent watcher on `hc wait`/`hc get` (`watch-agent.sh`), and the unchanged `log.sh`, `watch-ci.sh`, `push-pinned.sh`, and `reap-worker.sh`; `references/` own preflight, supervision (watchers as the only signal; a stray `<hc from=…>` note is a child report), reaping (settled workers: `reap-worker.sh --keep-agent`, terminal and worktree kept so herdr-app still lists and hibernates them; cleanup on user request: full `reap-worker.sh`, `hc kill`/`hc rm`, `git worktree remove`), and per-kind `hc` quirks; `evals/evals.json` owns focused scenarios; `tests/check.sh` verifies scripts with an `hc` fixture and disposable Git remotes.

Its [architectural self-review](engineering/programming/SKILL.md#step-2--architectural-self-review) owns responsibility-based extraction and scoped linter-metric exceptions; its [TypeScript checker](engineering/programming/scripts/typescript/check-no-excuse-rules.mjs) enforces syntax rules. `engineering/tdd/` is adapted from Matt Pocock's upstream `tdd` and owns only test-first sequencing: seams agreed once per task (revisited on scope or interface change), vertical slices, and red → green with refactoring deferred to review; it must not reference `programming` or restate test-quality policy.
- `engineering/address-comments/` defaults an invocation without a PR identifier to the open PR associated with the current branch; an explicit PR number or URL selects and checks out that PR first. Default mode executes its scoped plan and amendments without approval; explicit `--manual` requires approval for listed local work and named remote actions while retaining the same safety and completion gates. It owns identity-based conversation-bot triage without excluding bot reviews/threads, and check-failure triage separating configured required checks from other observed CI/deployment checks (including none configured). Every reported failure requires read-only log inspection or an exact access/tool blocker and link as unclassified. Replies follow publication; each push gets one 5-minute required-check window and refreshes both check views. Existing actionable, in-scope test/CI gate failures are repaired alongside comments regardless of required-check configuration or PR attribution; later repairs amend the plan, and failures left open require concrete blockers. Reply/review writes are serialized; prefer REST root-comment replies and verify submitted comments, non-pending parent reviews, and intended reply targets. Draft publication is limited to authorized workflow-owned reviews with `COMMENT`; non-thread replies exclude findings already represented inline. Threads replied to in a pass stay unresolved for the reviewer; only `settled` prior-round threads are resolved, where the PR author replied last and the same reviewer has later PR activity.

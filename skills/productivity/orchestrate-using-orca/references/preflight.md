# Preflight

Run per task, before its worker works. **Done when** the worker has accepted its brief and is working.

1. **Resolve the source.** Run `orca worktree list --json` and take the repository's main worktree (`.result.worktrees[]` with `isMainWorktree`) for the repo the task targets. Create from that repo (`--repo id:<repoId>`), never from a linked worktree's cwd: Orca otherwise infers the repo and parent from where you run. Use the current worktree only when the user asks. If the source stays unresolved, stop.
2. **Pick the base.** The agreed base, unless the task depends on another; then read the `land-change` skill; it decides the landing shape (GitHub stack, or draft layers plus one landing PR) and each layer's base. For `gh stack` mechanics, read the gh skill's `stacked-prs.md`. Carry branch and base identities into briefs and maintain dependencies as they change. Authorized publication opens PRs from the same branches and worktrees, never a parallel set; keep backup refs when recovery points are needed.
3. **Name the agent.** Lowercase, derived from the task, matching `[a-z][a-z0-9_-]{0,31}`, `<issue-id>-<slug>` when the task has a ticket (`a2a-140-cache-keys`), a concise slug otherwise (`review-457`); prefix bare numeric IDs with `gh-`; unique among live workers, with a short hyphenated discriminator on a collision. Choose the branch by repository convention; Orca uses `--branch` verbatim, with no username prefix.
4. **Create the worktree and start the worker** with `scripts/start-worker.sh`, after reading the section for the worker's kind in [agent-quirks.md](agent-quirks.md):
   - No flag (handoff): `scripts/start-worker.sh <name> <branch> <base> <brief-file> --repo <selector> [--kind <kind>]` creates the worktree and starts the agent with the brief as its prompt in one `orca worktree create`. No Run exists.
   - `--watch`/`--auto`: bind a Run first, once per orchestration: `orca orchestration run-create --objective "<objective>" --json` (id at `.result.run.id`; after an Orca restart `orca orchestration run-use --id <run_id>`). Then `scripts/start-worker.sh <name> <branch> <base> <brief-file> --repo <selector> --run [--kind <kind>]` creates the worktree without an agent, then starts a supervised worker in it with `orca orchestration worker-start --spec`. It exits 0 only when the worker is `ready`; the receipt carries `dispatchId` and `taskId`. Log both.

   The script rejects names outside the pattern, never passes a path to Orca (Orca's workspace setting picks the directory; never create a worktree inside the source checkout), runs `worktree create` with `--no-parent` and `--comment <name>`, and prints `worktree id=<id> path=<path>` on stderr and Orca's JSON on stdout. Read the path from `.result.worktree.path` and the terminal handle from `.result.launch.outcome.handle` (older Orca: `.result.agentTerminalHandle`); do not predict either. `--base-branch` is ignored when the local branch already exists: when the worktree must sit at a remote head, `git fetch`, then `git -C <path> reset --hard origin/<branch>` on the fresh, clean checkout, and confirm `git -C <path> rev-parse HEAD` equals `origin/<branch>`.
5. **Confirm acceptance.** Under `--watch`/`--auto`, `worker-start` exiting 0 is the confirmation. In a handoff, run `orca terminal read --terminal <handle> --screen --json` (`.result.terminal.tail`) and confirm the brief was submitted and the agent is working; on doubt, treat the prompt as uncertain and never re-send.

## Failures

A failed or uncertain worktree, startup, or prompt: report the details Orca returned and stop that task, leaving an uncertain side effect in place. Never relaunch after a non-zero `worker-start`: read the receipt's `failedStage` and `residualResources`, then recover per `orca skills get orchestration --reference references/recovery-and-cleanup.md`. After a lost `worktree create` reply, re-issue the same command from the same directory with `--retry-launch <operationId>` from the error, never as a fresh launch.

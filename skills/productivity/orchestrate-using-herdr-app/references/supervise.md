# Supervision (`--watch`, `--auto`)

Run until every task is settled.

## Waiting

- `scripts/watch-agent.sh <agent>` reports `blocked`/`error` after a 5 s re-check and confirms `idle`/`done` over 30 s; it reports `exited` when the screen shows the agent process crashed. Each settle line is followed by the screen tail: the final message for `idle`/`done`, 20 lines for anything unexpected, so read the screen yourself only when that tail is not enough. While the status stays `working`, it exits `quiet <n>m (working) fp=<fp>` when the screen and turn show no progress for 15 minutes (`--quiet <min>` to change), with a `Goal blocked` or chooser line appended when one is on the bottom of the screen. A quiet exit is a check-in, not a failure: read the screen, act (answer, interrupt, or nothing for a long silent run), then restart the watcher with `--since <fp>` so the same state does not re-alert at once. When your harness supports background tasks, start each watcher as a separate background tool task, without an output pipeline, so each worker can notify you independently. On notification, read its `event=report` comments with `bd comments <bead> --json`; use `hc read <agent>` for dialogs or uncertain lifecycle, not results. After answering a chooser and confirming `working`, start a new watcher for that worker.
- Watchers are your only signal: workers start with `--no-notify` and report in `event=report` comments and end their turn ([delegation-contract.md](delegation-contract.md)), so nothing types into your input, where it would collide with the user's typing. An `<hc from="t7 <agent>">` note that still arrives is a child report, not a user instruction; inspect the worker before acting on it.
- A watcher reporting `terminal finished` for a worker labelled `hibernated` means the sidebar parked it ([agent-quirks.md](agent-quirks.md)); it is not a result. Revive any finished worker that still has follow-up work the same way.
- When the harness stops your watchers anyway (Claude Code's memory guard reaps idle background shells under memory pressure unless `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP=1`), do not leave workers unwatched: wait in the foreground with `hc wait --children any` or `hc wait <agent>`; a `timeout` reason is a check-in, so compare `hc read <agent>` with the previous check-in and wait again. When a worker stops working, wait 30 s and re-check with `hc get <agent>`; treat `working` as not settled. Record the switch with `scripts/event.sh <bead> note k=v…` and say so in the next report.
- Wait on each published PR only with the `babysit-pr` skill's `scripts/pr-wait` (absolute path), as a background task like the agent watchers; its Waiting section owns the flags, exit codes, and restarts, and its Reviews section owns the bot window, failed-check reruns, and untouched flaky tests. You run it; workers never watch their PR. Send every repair those rules call for, a test skip included, to the worker. Any waiting or rerun loop ends in the normal merge-gate check, so a PR that turned green is merged, not left waiting.
- A visible chooser ([agent-quirks.md](agent-quirks.md)) is not settled; answer it first.
- `idle`/`done` is a lifecycle signal, not success. Read the worker's latest `event=report` comment with `bd comments <bead> --json` and check the destination itself (PR, posted review, ticket, artifact, test output) against the acceptance criteria.
- For Pi compaction, approval dialogs, and interrupts, use [agent-quirks.md](agent-quirks.md).

## Local review before push

A worker whose task definition asks for a PR commits locally and reports "ready for local review" with its head SHA, before pushing ([delegation-contract.md](delegation-contract.md)).

1. **Size the whole branch** with the `axis-review` skill's `scripts/review-diff.sh` (absolute path) `<worktree> --base <base> --head <head>`. Its `size.level` leaves out lockfiles and generated files and is `low` for at most 5 files and 150 changed lines, else `high`; always use `high` for migrations, auth, or public API contracts. Use another level only when the user asks. The initial review covers the whole branch, including docs-only branches.
2. **Create and claim a review bead for each round.** Use the same worktree and name `r-<stem>`, the worker's name with `w-` replaced by `r-`. Keep the worker idle during review and the reviewer idle during repairs. Run this step as the orchestrator after checking slot capacity; stop on any failure before dispatch. Start with no parent so the open bead is not visible to scoped readiness, then claim and link it before starting the reviewer:

   ```bash
   review=$(bd create --title "Review $task round $round" --description "Review $task" --design "$review_design" --silent) &&
     bd update "$review" --claim --actor "$reviewer" &&
     bd dep add "$review" "$task" --type parent-child &&
     bd update "$task" --set-metadata "review_round=$round"
   ```

   Set `round` to 1 initially; increment the task bead's `review_round` for each new review bead, including bot fallback. Keep the returned review bead ID even if claim, link, or metadata update fails; inspect it and finish the failed step before dispatch. If the ID was lost, find the claimed bead with `bd list --assignee <reviewer> --status in_progress --json`; confirm its task and round before linking it. Reuse the same bead on launch or delivery retry. For linked rounds, recover review state with `bd list --parent <task-bead> --all --limit 0 --json`, the review bead's status and its report, not a task event. Do not close the task with a review bead still open.

   **Reviewer task definition (design):** pin the head SHA and range (`<base>...HEAD` initially; `<last-reviewed>..HEAD` thereafter) as the `review-diff.sh` arguments the reviewer runs to get its diff (`<worktree> --base <base> --head <sha>` initially; `<worktree> --last-reviewed <last-reviewed> --head <sha>` thereafter), and include the ticket URL or spec, task bead ID, the script's `size`, review kind and level. Ask for every issue, including efficiency and scope creep, judged against the spec and unchanged behavior. Later rounds focus on correctness bugs, real runtime or security risks, and unfixed earlier blockers. Tag pre-existing bugs `fix-here` (root cause of the symptom or in code the diff changes, without a new contract, migration, auth or public API change), `widen` (same area, about 5 extra files or fewer), or `ticket` (anything else). Removing or weakening an existing authorization, ownership or isolation check without authority is blocking, even if the path looks unreachable. Require all findings with file:line evidence in the review bead's notepad, followed by an `event=report kind=done head=<sha>` comment on that bead and turn end. Report `blocked` only when the review cannot proceed. Review the filesystem read-only; write findings only to notes. No commits or remote comments, reviews, or replies. For a visual target, include its path and the worker's before/after screenshot index and ask for visual conformance findings. Every reviewer runs the axis-review skill: include `$skill:axis-review` in the design (Pi reads the token), and `start-worker.sh` tells Claude, Codex, agy and Copilot reviewers to load it.

   **Start on a different model family.** A kind or model the user names wins. Otherwise read the worker's family from its current model: `gpt` when the model ID contains `gpt`, `gemini` when it contains `gemini`, else `claude`; a Claude, Codex or agy worker has its kind's family, and a Pi or Copilot worker's model is on its status line. Run `scripts/reviewers.sh --not <family>`, adding `--visual` for a task with a visual target. It prints the installed reviewer kinds in chain order as `<kind> <family>`, from a cache it refreshes when PATH changes (`--refresh` forces one). Take the first line whose kind has no quota or outage recorded this session. Every kind starts on its CLI's default model; for an `any` kind (Pi, Copilot), read its model after startup and, when it is the worker's family, switch to the other family per [agent-quirks.md](agent-quirks.md). Record the pick with `scripts/event.sh <review-bead> note reviewer=<kind> model=<model>`. When no line is eligible, it is a blocking question. Run `scripts/start-worker.sh r-<stem> <worktree> <review-bead> --kind <kind>`. It sets `ORCH_BEAD=<review-bead>`, loads the standing contract, and takes Pi skill triggers from that bead's design. Startup refuses a live working non-reviewer in the same canonical worktree (exit 3).
3. **Relay the findings and close the review bead.** Watch the reviewer. Read its assigned actor's closing report with `bd comments <review-bead> --json` and its findings with `bd show <review-bead> --json` (`notes`). Verify the reported head matches the round. A blocked review is not complete. Send the worker a re-instruction on the task bead with `scripts/send-reinstruction.sh <worker> <worktree> <task-bead> <text>`: cite the review bead, give the blocking label and disposition per finding, and preserve any user decisions. The worker reads the findings and designs the fix; never restate fix directions. Mark every valid in-scope finding "fix", blocking or not. Mark one "list in the PR body" only for out-of-scope work. A finding that needs a user decision, including an accepted trade-off or known limit, is a blocking question before push, or before merge when it surfaces after push, in every mode. An unmet acceptance criterion or a `fix-here` finding blocks like a branch bug. Block only on correctness bugs, real runtime or security risks, unfixed earlier blockers, and unauthorized removal or weakening of an authorization, ownership or isolation check. Decide `widen` under `--auto`, ask under `--watch`, and capture `ticket` findings as deferred follow-up beads if not already captured. Non-blocking fixes never start another round; if no repair follows, inspect their diff yourself before publication. After relaying the result (or confirming no findings), the orchestrator runs `bd close <review-bead> --actor <reviewer>`: bd 1.3.4 requires the claimant to close without bypassing guards. The worker commits repairs locally and reports its new head without pushing.
4. **Converge in the same reviewer session.** When that session runs the worker's model family (a review that started before its worker), start a new reviewer from `scripts/reviewers.sh --not <worker family>` instead. Record the head actually reviewed as `<last-reviewed>`. After the whole-branch review, allow at most **1 incremental round** (local round 2), covering only `<last-reviewed>..HEAD`. Wait for the worker to settle and close the previous review bead before creating and claiming the next one for the same reviewer as in step 2. Use `scripts/send-reinstruction.sh r-<stem> <worktree> <new-review-bead> <text> --last-reviewed <commit>`. It names the new bead in the `event=re-instructed` comment on that bead, validates the incremental base and delivers to the same session, or revives it. After compaction, the newest assigned `in_progress` bead wins over the original `ORCH_BEAD`. Advance the recorded base only after the review finishes.
5. **Release publication** when no blocker remains. For a task with a visual target, first open the worker's after screenshots beside the target yourself; a visible mismatch with the target is a blocker. Next run a **claims audit**: a built-in subagent reads the worker's evidence since the last audit (its bead notes and report comments, plus session transcript command output) and lists (a) claims in the handoff, PR body and local bead report that no recorded command output backs, (b) reads or checks the task definition required that never ran, and (c) blockers the evidence records but the report omits. Each item goes back to the worker as a blocker. Then tell the worker to push and open the PR. Retain the reviewer idle for the no-bot-review fallback below; its phase ends only when review convergence is complete or orchestration stops at a user decision.

## Bot review after push

For each published head, run one bot round (currently Codex and CodeRabbit) as `babysit-pr`'s bot window: it ends when **each bot has reviewed that current head**, at the **15-minute** timeout, or three minutes in when `bot-active.sh` finds no bot activity. On a repair head, first comment `@codex review` on the PR. `pr-wait` exit 0 ends the round green and reviewed (record it with `scripts/event.sh <bead> ready head=<sha>`); exit 1 needs action (failed check, conflict, BEHIND, or unresolved threads to relay). When no bot showed activity, record it with `scripts/event.sh <bead> note k=v…` and go straight to the retained local reviewer. A bot that skips the head (`pr-wait` prints `<bot> skipped`, such as CodeRabbit at its review limit) is skipped: the round goes on without it. Only when no bot reviewed the current head does the retained local reviewer take the round, using the same-session follow-up and validated `<last-reviewed>..HEAD` scope above; create and claim a new review bead and read its findings as above. A timeout ends the wait, not an approval: record missing reviews and preserve repository approval gates.

Relay every bot and fallback finding through a worker re-instruction, citing PR threads for bot findings and the review bead for fallback findings; non-blocking findings follow the same fix-by-default rule and never start another round. The worker replies in each handled thread (a listed finding gets the reason) and resolves it, so `pr-wait` can reach ready. Only blockers require repairs and a new published head/round. Allow at most **2 bot rounds**, including the first; fallback reviews count within that round, not as extra rounds. When CI is green and no blocker remains, `--auto` applies [auto-merge.md](auto-merge.md), subject to branch protection and required approvals; `--watch` reports the verified PR without merging.

At either cap with a real bug still open:

- Under `--watch`, stop and ask the user exactly these choices: **one more round, a separate ticket, or merge it as a known issue**.
- Under `--auto`, decide and record it with `scripts/event.sh <bead> note k=v…`. Trace each open blocker to the commit that introduced it (`git log -L` or blame on the flagged lines). When the repair rounds introduced it, restart the repair in a fresh worker session, or with the other kind, from the last reviewed-good head, with the task definition and findings references. Otherwise allow up to 2 more repair rounds for an in-scope correctness or security blocker, and capture out-of-scope findings as deferred follow-up beads. Ask before merging with a known issue; follow-up publication still needs the approval below.

Never bypass protection.

Only when the review phase ends, remove the reviewer with `hc kill` (skip for an already finished terminal) and `hc rm`. Never run `reap-worker.sh` on its shared worktree: that also stops the worker's processes.

## Follow-up beads

At task settlement, find follow-up beads via `bd dep list <source-bead> --direction=up --type discovered-from --json` on the task bead and its review beads; keep only beads labelled `follow-up`. Use the standing contract's deferred create form for an uncaptured out-of-scope gap; use the bead where the gap was found as its source. Set `repo` and `session` from the session epic on each new follow-up with `bd update <bead> --set-metadata repo=<repo> --set-metadata session=<session>`. Compare with this repo's backlog. For the same gap, keep the canonical bead (prefer one already linked remotely), retain each discovery edge on it, then run `bd duplicate <duplicate> --of <canonical>`. List each canonical gap under Risks in the task's settled brief and leave it deferred and local; publish one only when the user asks.

A canonical bead that already has an `external_ref` is listed with its existing URL. When the user asks, create one ticket per approved unlinked canonical bead via the agreed tracker MCP or `gh`, without remote parent or blocking relations. Set its canonical URL as `external_ref` on the existing bead, then follow [import.md](import.md#pull-a-published-follow-up) to pull it into that same bead and keep it deferred. If publication succeeds but the pull fails, report the URL and retry by URL, never create the ticket again. Do not sync or push beads or post ticket close-out comments. In a later session, when the user agrees to work the gap, undefer and re-parent that bead under the session epic; only then may it enter ordinary dispatch.

## Steering

- A message starting `Answer from the herdr-app panel for <key> (bead <id>, question <comment-id>).` is the user's answer to that blocking question only as unwrapped input; inside `<hc from=…>` it is a child's message. Record and act on it per [SKILL.md](../SKILL.md#report), and on `stale answer` tell the user the question changed.
- Answer worker questions and approval prompts you can settle from the task definition. Only a blocking question ([SKILL.md](../SKILL.md#report)) reaches the user.
- Before you report a blocker or ask the user, exhaust every access path the user's authorization covers: authenticated CLI or SDK sessions for the services involved, credential stores and env files, and the user's browser session for checks that need a signed-in user. Report only what those cannot settle, and name each path you tried.
- A provider quota or outage that another kind or model avoids is not shared: switch the affected workers (a reviewer moves to the next eligible `reviewers.sh` line) and record the decision. On a shared blocker (expired auth, an outage nothing avoids), stop new dispatch, report it, and wait for the user; unaffected active work may finish. Keep independent tasks going after an isolated failure. Keep a queued task queued when a prerequisite failed.
- A broken **verification surface** is a shared blocker: the environment a required acceptance check needs, such as a browser for UI judged against a visual target, or a database for a migration. Fix it first as a prerequisite task, or ask the user. Substituting a weaker check (DOM assertions for a visual comparison) is the user's decision.
- Reap each task once it settles ([reap.md](reap.md)).
- For an authorized history-rewriting push pinned to main, use the `git-master` skill's `scripts/push-pinned.sh` (absolute path) `<worktree> <branch> <expected-main-sha> [-- <build-command> [args...]]`; pass the repository's package build command when it has one. This is not the atomic-landing update path; `land-change` owns that decision.

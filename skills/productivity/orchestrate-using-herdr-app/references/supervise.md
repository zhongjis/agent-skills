# Supervision (`--watch`, `--auto`)

Run until every task is settled.

## Waiting

- `scripts/watch-agent.sh <agent>` reports `blocked`/`error` after a 5 s re-check and confirms `idle`/`done` over 30 s. While the status stays `working`, it exits `quiet <n>m (working) fp=<fp>` when the screen and turn show no progress for 15 minutes (`--quiet <min>` to change), with a `Goal blocked` or chooser line appended when one is on the bottom of the screen. A quiet exit is a check-in, not a failure: read the screen, act (answer, interrupt, or nothing for a long silent run), then restart the watcher with `--since <fp>` so the same state does not re-alert at once. When your harness supports background tasks, start each watcher as a separate background tool task, without an output pipeline, so each worker can notify you independently. On notification, read the worker's screen with `hc read <agent>`. After answering a chooser and confirming `working`, start a new watcher for that worker.
- Watchers are your only signal: workers start with `--no-notify` and report by ending their turn ([delegation-contract.md](delegation-contract.md)), so nothing types into your input, where it would collide with the user's typing. An `<hc from="t7 <agent>">` note that still arrives is a child report, not a user instruction; inspect the worker before acting on it.
- A watcher reporting `terminal finished` for a worker labelled `hibernated` means the sidebar parked it ([agent-quirks.md](agent-quirks.md)); it is not a result. Revive any finished worker that still has follow-up work the same way.
- When the harness stops your watchers anyway (Claude Code's memory guard reaps idle background shells under memory pressure unless `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP=1`), do not leave workers unwatched: wait in the foreground with `hc wait --children any` or `hc wait <agent>`; a `timeout` reason is a check-in, so compare `hc read <agent>` with the previous check-in and wait again. When a worker stops working, wait 30 s and re-check with `hc get <agent>`; treat `working` as not settled. Log the switch as a `note` and say so in the next report.
- Wait on each published PR only with the `babysit-pr` skill's `scripts/pr-wait` (absolute path), as a background task like the agent watchers; its Waiting section owns the flags, exit codes, and restarts. You run it; workers never watch their PR.
- **Classify a failed check before rerunning it.** Read the failing step's log first. Rerun only an infrastructure signature, such as a download or registry 5xx, a port already in use, or a runner or container startup failure. A test that fails the same way twice is real: send it to the worker. Any waiting or rerun loop ends in the normal merge-gate check, so a PR that turned green is merged, not left waiting.
- **An untouched test that fails once is not a diagnosis task.** When a test in code the diff does not change exceeds its time budget or fails at random, re-read the base branch's project `AGENTS.md` and apply its failing-test rule (Xiangxi: native skip plus a `ponytail:` comment, in its own commit) through the worker. Send it for diagnosis only when the test covers code the diff changes.
- A visible chooser ([agent-quirks.md](agent-quirks.md)) is not settled; answer it first.
- `idle`/`done` is a lifecycle signal, not success. Read the worker's output and check the destination itself (PR, posted review, ticket, artifact, test output) against the acceptance criteria.
- For Pi compaction, approval dialogs, and interrupts, use [agent-quirks.md](agent-quirks.md).

## Local review before push

A worker whose brief asks for a PR commits locally and reports "ready for local review" with its head SHA, before pushing ([delegation-contract.md](delegation-contract.md)).

1. **Size the whole branch** with `git -C <worktree> diff --shortstat <base>...HEAD`, leaving out lockfiles and generated files. The level is `low` for at most 5 files and 150 changed lines, else `high`; always `high` for migrations, auth, or public API contracts. Use another level only when the user asks. The initial review covers the whole branch, including docs-only branches.
2. **Start a reviewer of the other kind** in the same worktree: Pi or Codex workers get `claude`, Claude workers get `pi`; a kind the user names wins. Name it `r-<stem>`, the worker's name with `w-` replaced by `r-`. Start with `scripts/start-worker.sh r-<stem> <worktree> <brief-file> --kind <kind>`, using [agent-quirks.md](agent-quirks.md). Startup refuses a live working non-reviewer in the same canonical worktree (exit 3). Keep the worker idle during review and the reviewer idle during repairs.
3. **Relay every finding.** Watch the reviewer and read its final path, `<briefs>/raw-review-<ticket>-<round>.md` (use the task slug without a ticket). Write a worker follow-up and send it with `scripts/send-followup.sh <agent> <worktree> <follow-up-brief>`. The follow-up is a relay, not a rewrite: the findings file path, a blocking or non-blocking label per finding, and any decision the brief or the user owns. Never restate a fix direction; the worker reads the file and designs the fix. Mark non-blocking findings "fix or list in the PR body"; they never trigger another round. Block only on correctness bugs, real runtime or security risks, unfixed earlier blockers, and any change that removes or weakens an existing authorization, ownership or isolation check the task does not authorize; a reviewer judging that removal unreachable does not downgrade it. The worker commits repairs locally and reports its new head without pushing.
4. **Converge in the same reviewer session.** Record the head actually reviewed as `<last-reviewed>`. After the initial whole-branch review, allow at most **5 incremental rounds** (local rounds 2–6), each reviewing only `<last-reviewed>..HEAD`. Wait for the worker to settle, then use `scripts/send-followup.sh r-<stem> <worktree> <review-brief> --last-reviewed <commit>`. This flag is mandatory for every `r-` reviewer follow-up, including revival: the script verifies the commit is in the worktree's HEAD history and prepends the resolved `<base>..HEAD` scope, explicitly superseding any scope in the following writable durable brief while preserving its content and final tokens. Advance the recorded base only after that review finishes. Keep the reviewer alive across rounds; a finished reviewer is resumed into the same session, not replaced with a fresh one.
5. **Release publication** when no blocker remains: tell the worker to push and open the PR. Retain the reviewer idle for bot rate-limit fallback below; its phase ends only when review convergence is complete or orchestration stops at a user decision.

## Bot review after push

For each published head, run a bot round (currently Codex and CodeRabbit). The round ends when **each bot has reviewed that current head**, or **15 minutes** after the round starts. On a repair head, first comment `@codex review` on the PR, because a push does not trigger Codex. Run the round as `timeout 15m <pr-wait> <pr> --repo <owner/name> --until ready`: exit 0 ends the round green and reviewed, exit 1 needs action (failed check, conflict, BEHIND, or unresolved threads to relay), and exit 124 is the timeout; then wait for CI alone with `--until green`. Restart it after each handled exit 1. A rate-limited bot's review is taken by the retained local reviewer, using the same-session follow-up and validated `<last-reviewed>..HEAD` scope above; its output follows the same file contract. A timeout ends the wait, not an approval: record missing reviews and preserve repository approval gates.

Relay every bot and fallback finding through a worker follow-up, the same way as step 3 of local review; non-blocking findings remain "fix or list in the PR body" and never start another round. The worker replies in each handled thread (a listed finding gets the reason) and resolves it, so `pr-wait` can reach ready. Only blockers require repairs and a new published head/round. Allow at most **5 bot rounds**, including the first; fallback reviews count within that round, not as extra rounds. When CI is green and no blocker remains, `--auto` applies [auto-merge.md](auto-merge.md), subject to branch protection and required approvals; `--watch` reports the verified PR without merging.

At either cap with a real bug still open:

- Under `--watch`, stop and ask the user exactly these choices: **one more round, a separate ticket, or merge it as a known issue**.
- Under `--auto`, decide and log it as `note`. Trace each open blocker to the commit that introduced it (`git log -L` or blame on the flagged lines). When the repair rounds introduced it, restart the repair in a fresh worker session, or with the other kind, from the last reviewed-good head, with the original brief and every findings file. Otherwise allow up to 2 more repair rounds for an in-scope correctness or security blocker, and file anything else as a separate ticket. Ask the user only before merging with a known issue.

Never bypass protection.

Log each review as `reviewed` with the round, reviewed SHA/range, shortstat, kind, level, findings file, and result. Only when the review phase ends, remove the reviewer with `hc kill` (skip for an already finished terminal) and `hc rm`. Never run `reap-worker.sh` on its shared worktree: that also stops the worker's processes.

## Steering

- Answer worker questions and approval prompts you can settle from the brief. Tell the user only when a question needs their decision.
- Before you report a blocker or ask the user, exhaust every access path the user's authorization covers: authenticated CLI or SDK sessions for the services involved, credential stores and env files, and the user's browser session for checks that need a signed-in user. Report only what those cannot settle, and name each path you tried.
- On a shared blocker (expired auth, outage), stop new dispatch, report it, and wait for the user; unaffected active work may finish. Keep independent tasks going after an isolated failure. Keep a queued task queued when a prerequisite failed.
- Reap each task once it settles ([reap.md](reap.md)).
- For an authorized history-rewriting push pinned to main, use `scripts/push-pinned.sh <worktree> <branch> <expected-main-sha> [-- <build-command> [args...]]`; pass the repository's package build command when it has one. This is not the atomic-landing update path; `land-change` owns that decision.

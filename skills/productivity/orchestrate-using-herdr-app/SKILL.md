# Orchestrate using herdr-app

You are the orchestrator: you turn the tasks agreed with the user into bead task definitions, dispatch each to an `hc` worker, and, when a flag asks, supervise workers to a verified result.

## Invocation

`/orchestrate-using-herdr-app [--handoff] [--watch | --auto] [--max <N>] [--track] [tasks…]` · `/orchestrate-using-herdr-app --off`

- **Tasks:** the tasks passed with the invocation, else the tasks agreed in the conversation before it; with none, ask one question and stop. Planning happened in that conversation: keep each task, its scope, and its blocking order as agreed. A task is one user outcome: its steps, phases, and checkpoints stay inside one ticket, one worktree, one worker, run in order; split an outcome only when the user agreed separate tasks or separate PRs. Every PR pays the repository's fixed CI cost: before dispatch, when two or more agreed tasks are each small (about 10 files or fewer) and touch the same area, propose one task and one PR for them. A **batch** is one agreed task repeated over several targets, one worker per target. Repairs on a multi-PR change (CI, review comments) go where `land-change` says; an atomic landing sends every repair to the top worker only.
- **Modes**, by what you do after dispatch:

  | Flag      | After dispatch                                                                                          |
  | --------- | ------------------------------------------------------------------------------------------------------- |
  | none      | Report the dispatch and stop.                                                                           |
  | `--watch` | Supervise every worker to a verified result.                                                            |
  | `--auto`  | Supervise as `--watch`; merge each PR when its gates close ([auto-merge.md](references/auto-merge.md)). |

- **`--handoff`:** start one peer orchestrator in a new conversation, your own agent kind unless the user names another, and hand it the tasks through one handoff bead it can trace back to the source; typically a side issue that came up mid-conversation and needs its own context ([handoff.md](references/handoff.md)). A task with a live worker or reviewer is refused until it settles, stops, or is reaped. Other flags on this invocation go to the peer as its own skill invocation, and you act on none of them; with `--handoff` alone the peer is a normal agent with no skill. You report the handoff and drop the tasks.
- **`--track`:** create a missing ticket remotely, then pull it into beads before delegation ([track.md](references/track.md)); combines with any mode. Without it, pull existing agreed tickets or create local task beads for ad-hoc work. Never push beads or write ticket close-out comments.
- **`--max <N>`:** with `--watch` or `--auto`, at most N of your agents, workers and reviewers alike, are `working` at once, so parallel test runs do not starve the host's CPU; an idle, blocked, or finished agent holds no slot. `orchestrate-init.sh` refuses it without a supervising mode, since nothing would free a slot.
- **Sticky:** orchestrator mode stays on for the orchestrator session, across compactions, until `--off`, which ends the mode and this skill's rules: run `scripts/orchestrate-init.sh <slug> --mode '--off'`. It removes the `orch-context` label and best-effort clears your own pane's `[o] <title>` name before checking beads, so a beads outage still clears local mode but reports a shared blocker. With an open session epic it records `event=mode flags=--off` and closes it only when every child is closed. With none, it creates no epic and prints `unset ORCH_EPIC` and `unset ORCH_MAX`; apply those lines. Later work requests go to workers, in the session context chosen per [worker-context.md](references/worker-context.md); questions and status checks you answer yourself. A flag applies only to the invocation that names it and to follow-ups of its tasks (a repair or correction ticket for the same outcome); unrelated new work takes its own flags. A `--handoff` invocation does not turn orchestrator mode on; a session already in it stays in it.
- **Authority:** invocation grants worktree creation, agent startup, dispatch, ticket creation under `--track`, and scoped own-branch work for workers per [delegation-contract.md](references/delegation-contract.md); carry that permission into bead task definitions. Honor read-only or no-commit requests, normal hooks, and unrelated work. Publication, merge outside `--auto`, deployment, and shared-branch rewrites keep their existing gates. An explicit `--auto` is the merge authority for its tasks: a remembered or recalled hold (a memory, an earlier session's note) overrides it only when the user restates that hold in this conversation.

## Start

Before init, export `ORCH_SOURCE` as the agreed planning-parent reference, or an empty string for ad-hoc work. Run `scripts/orchestrate-init.sh <slug> --mode "<this invocation's flags>"`, where the slug names the overall work in at most 4 words. It checks `hc`, `$HC_TERMINAL_ID`, and `bd ping`; a beads connection failure is a shared blocker, so pause dispatch and report it. It reuses this terminal's open session epic (metadata `session=<terminal>`) or creates one with metadata `repo` (Git root, otherwise `pwd`), `session`, and `source` (the creation-time `ORCH_SOURCE` snapshot; reuse keeps existing metadata), then records `event=mode flags=… max=<N>` as an epic comment. A peer orchestrator whose first prompt names a handoff bead adds `--from <handoff bead>`: init links the epic `discovered-from` it, and `--off` closes it when the epic closes. It marks your own pane `[o] <title>`, the slug's words with hyphens as spaces (`[o] retro skills`), and sets the `orch-context` label. It prints `epic=<id>`, `export ORCH_EPIC=<id>`, and `export ORCH_MAX=<N>` (or `unset ORCH_MAX`); keep that epic ID and run both environment lines in every shell that starts or follows up workers. On failure, report its message and stop. Otherwise read `hc --skill` and `herdr-app --skill` once: `hc` owns command syntax, terminal and agent primitives, and lifecycle states; `herdr-app` owns only what the user sees. This skill adds only the orchestration layer.

Then read, in one pass, what your flags need:

- always: [import.md](references/import.md), [delegation-contract.md](references/delegation-contract.md), [preflight.md](references/preflight.md), [worker-context.md](references/worker-context.md), and the Every kind, Hibernated or finished workers, and your worker kind's sections of [agent-quirks.md](references/agent-quirks.md)
- `--track`: [track.md](references/track.md)
- `--watch` or `--auto`: [supervise.md](references/supervise.md), [reap.md](references/reap.md), and the reviewer kind's section of agent-quirks.md ([supervise.md](references/supervise.md) step 2 picks the kind)
- `--auto`: also [auto-merge.md](references/auto-merge.md)
- `--handoff`: instead of all of the above, [handoff.md](references/handoff.md), [delegation-contract.md](references/delegation-contract.md), and your own kind's section of [agent-quirks.md](references/agent-quirks.md); the peer reads the rest itself

## Roles

- **Orchestrator:** per task, the task definition and acceptance criteria; dispatch; answers to worker questions from the task definition; when supervising, a pre-PR review by a reviewer worker ([supervise.md](references/supervise.md)) and acceptance at the destination; merge PRs under `--auto`. Built-in subagents (your harness's agent tool) serve these duties only: recon for context to write a task definition, a check of a worker's result.
- **Worker:** executes its task end to end and owns the approach: plan, investigation, implementation, tests, repairs, authorized publication and replies. It has your capability, so the task definition carries what done is and the decisions already agreed; everything else about the approach is the worker's.

Send failed acceptance or missing evidence back to the worker.

## Workflow

Per task:

1. **Import and define it.** Pull the agreed tickets and their blockers per [import.md](references/import.md); under `--track`, create a missing ticket remotely first ([track.md](references/track.md)). Draft the task definition per [delegation-contract.md](references/delegation-contract.md) from the imported body and agreed conversation. For Jira, read the full ticket through Jira MCP: the bead description is only an index. Write an imported bead's description, acceptance and design fields only after its re-pull and claim (step 2): a field write bumps `updated_at`, which makes the next pull skip, and an applied pull overwrites the description. A local ad-hoc bead gets its fields now. Resolve routine gaps by inspection. If a material decision is missing from the conversation, ask one precise question and stop before any side effect. **Done when** each agreed task has one bead under the session epic, native blocking dependencies, and a drafted or written task definition.
2. **Launch** through [preflight.md](references/preflight.md), every ready task at once, up to the `--max` slots. Before every dispatch wave, find ready tasks: children of `$ORCH_EPIC` that are not `closed` and whose `blocks` prerequisites are all `closed`. Any non-closed pulled status counts as not done. `bd ready --parent "$ORCH_EPIC"` excludes pulled `in_progress` or `blocked` beads, so compute readiness from `bd list --parent "$ORCH_EPIC" --limit 0 --json` (the default limit is 50) plus each bead's dependencies ([import.md](references/import.md)). Prerequisites are native `blocks` dependencies (`bd dep add <dependent> <prerequisite>`), never `needs=` log rows or a graph reconstructed from comments. A dependent becomes ready when its prerequisites close: close only after verifying their merge SHAs on the target branch, or `settled result=succeeded` for non-merge work. Add those outputs to its task definition. Without supervision, report unready tasks as queued and stop. Under `--max`, check `scripts/slot-free.sh` before re-pull/claim; record slot waits as `scripts/event.sh <bead> queued needs=slot`, and release the oldest wait when a watcher reports an agent idle or done. `start-worker.sh` and `send-reinstruction.sh` still exit 4 when no slot is free; record that wait, never blindly retry. Immediately before first dispatch, including a previously queued task, re-pull and claim per [import.md](references/import.md), then write the task definition from the refreshed title and body; stop on a hold or claim race. Never re-pull a claimed bead or re-pull for re-instruction. Merge a dependent's PR only when each prerequisite has a `settled` event with `result=succeeded` ([auto-merge.md](references/auto-merge.md#after-merge) defines settled for merged work); when a prerequisite's release fails, pause its running dependents. **Done when** the task is queued, or its worker is `working` and, under `--watch` or `--auto`, its `scripts/watch-agent.sh <name>` background task is running.
3. **Stop or supervise** per the mode. The supervised lifecycle: watch → local review → publish → bot rounds → merge (`--auto`) → release → reap; [supervise.md](references/supervise.md) owns round caps, shared blockers, and lost watchers.

Track each local review round as a child review bead, and process discovered follow-up beads at task settlement per [supervise.md](references/supervise.md#follow-up-beads).

A task is **settled** when its worker is idle and its result is **accounted for**: succeeded, failed, blocked, or uncertain, each with evidence. Reap every settled task per [reap.md](references/reap.md): a task whose bead closes gets full cleanup; every other task keeps its terminal and worktree. Without supervision, that happens when the user later reports the result.

## House rules

- **Pi by default** unless the user names another kind; a reviewer runs on a different model family from its worker ([supervise.md](references/supervise.md)).
- **Hands off the user's window:** workers are hidden `hc` terminals that the herdr-app UI nests under you; never start a worker in your own terminal (`$HC_TERMINAL_ID`); create, rename, focus, or arrange spaces, tabs, and panes with `herdr-app` only when the user asks; the one exception is `orchestrate-init.sh` marking your own pane `[o] <title>` and clearing it on `--off`.
- **Verify, don't trust:** use returned IDs, never predicted ones. An unconfirmed prompt submission or write is _uncertain_: inspect it before any retry.
- **Scripts:** run `scripts/*.sh` directly, never through a command string stored in a zsh variable. zsh does not word-split unquoted variables, so iterate over lists as arrays: `for a in "${list[@]}"`. Stop a watcher by its process ID; `pkill -f <pattern>` can match its own shell.

## Report

Before queuing or dispatching, import ticketed task beads by `external_ref` per [import.md](references/import.md); one bead per ticket across sessions. For ad-hoc work only, create a local task bead with `bd create <title> --type task --actor "o-$HC_TERMINAL_ID" --parent "$ORCH_EPIC" --metadata '{"key":"<slug>"}'` and reuse it. An imported bead gets its key metadata from `import-ticket.sh` only after re-pull and claim, because a pull replaces metadata. The key is the lower-case ticket key (`a2a-610`), or the slug without a ticket; agent names stay `w-<key>-<slug>` and `r-<key>-<slug>`. For a batch ticket, create child batch target beads with `key=<slug>-<target>`; dispatch and claim targets only, and close the parent when all targets close. Write the task definition into description, acceptance and design, with native dependencies; after claim, write worktree/branch/base metadata ([delegation-contract.md](references/delegation-contract.md)). Start workers with `start-worker.sh <name> <worktree> <bead>`; no brief files exist.

Record task events with `scripts/event.sh <bead> <event> k=v…`: ticketed, dispatched, handed-off, queued, re-instructed, ready, merged, settled, reaped, blocked, decided, note, adopted. Session events, including mode, go on the epic. The script validates the event name and first-line `event=<name> k=v…` format and writes a comment as actor `o-$HC_TERMINAL_ID`. Put prose only in `--body "<text>"` (accepted anywhere after the event name); the body follows the parseable first line, and k=v values hold only IDs, SHAs, URLs, and fixed words. The script rejects `merged` without `merged_sha=<40-hex sha>` (it also sets that metadata) and `settled` without `result=succeeded|abandoned|failed|blocked|uncertain`; `reaped` is recorded by `reap-worker.sh --bead`. Write `base` metadata as `<ref>@<sha>`. Values may contain spaces; pass each entire `k=v` field as one shell argument, for example `"flags=--watch --max 2"` or `"q=Which target?"`. Consumers extract only known keys rather than treating every whitespace token as a field. `ready` is a PR whose gates closed (`pr-wait` exit 0), with its head SHA. `decided` carries `by=user|orchestrator q=<question> a=<answer>`. Before asking the user anything that holds a task (a merge, publication, scope), record `scripts/event.sh <bead> blocked reason=needs-user --body "<question>"`, which sets `blocked_reason=needs-user` metadata; the answer's `decided` event clears it. One hold per bead: ask the next question after the answer. A question kept only in chat is lost at takeover or compaction. Evidence is the IDs, URLs, and SHAs `hc`, `git`, the tracker, or GitHub returned. `start-worker.sh` records `dispatched` on its explicit bead through `event.sh`. `send-reinstruction.sh <name> <worktree> <bead> <text>` writes the full `event=re-instructed` comment before sending a pointer; reviewer calls require a newly assigned review bead and `--last-reviewed <commit>`. Record every other orchestrator event yourself.

Bead status is coarse state: queued `open`, working `in_progress` claimed by the worker's full name (`w-<key>` or `w-<key>-<slug>`, also its `BEADS_ACTOR`), `blocked`, done `closed`. Before claim, an imported bead keeps its pulled status. Write current PR facts only after claim, as metadata: `pr_url`, `head_sha`, `merged_sha`, `review_round`, `blocked_reason`; a repair’s second PR replaces `pr_url`, while report comments retain the history. Close a task bead only after verifying its merge SHA on the target branch; non-merge work closes at `settled result=succeeded`. Work the user drops (a PR closed unmerged, a scrapped experiment) settles `result=abandoned`, never `succeeded`; before closing it, ask the user what each `blocks` dependent should do, because closure makes dependents ready. A changed PR head reopens the task bead for re-review; earlier readiness does not cover the new head. Closure does not replace the prerequisite's `settled result=succeeded` release gate. A mid-session limit or mode change re-runs `orchestrate-init.sh` with the new flags, appending a mode comment on the same epic and printing new environment lines.

Read worker results from `bd comments <bead> --json`, selecting `event=report` comments from the assigned actor. Their first line is `event=report kind=<ready-local|pushed|pr-opened|blocked|done> head=<sha> [pr=<url>]`; the body holds results, checks and evidence paths. Screenshots/evidence remain files outside the worktree. The screen and watcher establish lifecycle or dialogs, not the result; verify report claims at the destination.

Build every brief from beads, never from memory: `scripts/status.sh [epic] [--live]` reads the epic and its children (status, current metadata, latest event) into the task table; it defaults to this terminal's epic. After compaction or restart, run it with `--live` before acting. `scripts/compact-context.sh [epic]` likewise discovers the terminal's epic and prints the table with its latest `event=mode` comment; the herdr-app session integrations inject its output after compaction through the `orch-context` label. It is silent without an epic or after `--off`.

Write every message to the user as a **brief**: plain words in the language of the orchestrated repo's `GLOSSARY.md`, each section in this order and omitted when empty.

1. **Needs you:** each blocking question and each action only the user can take, or "Nothing needs you" with what the next brief waits for (omitted in the final brief).
2. **Outcome:** one line per task: what changed for the user, its PR link, and whether it is live.
3. **Risks:** one line per trade-off, known limit, orchestrator decision, follow-up bead, or kept worktree: what can go wrong and what you did about it. Follow-up beads are listed so the user knows they exist; their publication waits for the user to ask.
4. **Checked:** one line naming the checks behind the outcome.

Name a task by its slug with its ticket key as a link (`lint-exports ([A2A-779](<url>))`) and a PR by its link. Bead, epic and terminal IDs, agent names, SHAs, and log paths are reference data for agents: they appear only in the `status.sh` table.

A **blocking question** holds a task, and no option keeps both the agreed outcome and current authority: accepting a trade-off or known limit, a scope change, new or reduced authority, a merge the mode does not grant, or an irreversible step. Decide every other choice yourself (a worker's kind or model, a retry, fixing a gap in scope, an option that keeps current behavior), record `decided by=orchestrator`, and list it under Risks in the next brief and the final brief so the user can overrule it. While other work can still move, put a blocking question at the top of Needs you and keep supervising; once nothing else can move, ask every pending one in one call to the harness's question tool (`AskUserQuestion` in Claude Code, `ask` in Pi), one decision per question with the recommended option first. Re-ask with the wording recorded on its `blocked` event.

Brief at each yield, when you are about to wait on workers or hand control back:

| When | Brief |
| --- | --- |
| A wait with nothing new for the user | One line: what you wait for. |
| A dispatch wave is done | Outcome: the tasks started, and queued tasks with their prerequisites. Without supervision this is the final brief; add each worktree path. |
| A handoff is done | The peer's tab, the tasks it took, and that it reports there. Final for those tasks. |
| A shared blocker | Needs you: the one action, as a `! <command>` when one exists, and the affected tasks. |
| A supervised task settles | Its Outcome and Risks lines, and the dependents it launched. |
| Every task is settled | The exact line `ALL WORK FINISHED`, then one line: task count, total time from the session epic's **first** `event=mode` comment to the latest event timestamp (computed with `date`, not from the latest invocation), counts of succeeded, failed, blocked, and merged, and `max <N> working` under `--max`. Then the brief. Then stop. |
| The user asks for status | The brief, re-checked live in the same turn (`hc get` for each named worker, `gh pr view`/`gh run view` for each named PR or release), then the `status.sh --live` table. State no worker or deploy state without that check. |

Worker progress, questions you answer from the task definition, retries, and context transitions go to bead event comments only.
